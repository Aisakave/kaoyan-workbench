## 方案（已实现）

### I-12 `.gitignore`

增加 `backup-*.jsonl`，与既有 `backup-*.json` 并列。零风险、零依赖。

### I-02 导入前配额预检

在 `importAll()` **任何写入之前**：

1. `navigator.storage.estimate()` 取 `quota - usage` 为可用空间；
2. 需求量按备份文件体积 × 0.8 估算（base64 解码后约占 75%，余量留给缩略图）；
3. 需求 > 可用 → 弹确认弹窗（标题「存储空间可能不足」，正文给出「约需 X / 本机仅剩 Y」+ 失败会自动撤销的承诺），按钮「取消 / 仍要导入」；
4. 取消 → 直接返回，不写任何数据；继续 → 走正常导入；
5. 预检本身异常（无 API 或 `estimate()` 失败）**不拦截**导入——已有 I-01 回滚兜底。

### I-01 导入失败自动回滚

- 进入导入前记录 `preExisting = Set(Store.imageKeys())`：导入前已存在的原图 ID 快照；
- 每张图 `saveImage` 成功后立即登记进 `written`（覆盖「图片已落库但缩略图生成失败」的场景）；
- 任一步失败 → 遍历 `written` 调 `Store.deleteImage`（同时删原图与 `t_` 缩略图键）；
- **`preExisting` 中的 ID 跳过不删**：重导同一份备份、或备份与现有数据有交集时不会误删旧图；
- 回滚阶段单独提示「导入出错，正在撤销已导入的内容…」；清理失败的张数计入文案。

### I-03 错误文案分类

新增内部辅助 `importFail(msg)`（标记用户可读错误）与 `importErrMsg(e, hadWritten, cleanupFailed)`：

| 情况 | 文案 |
|---|---|
| 首行无法解析 | 这不是有效的备份文件（首行不是备份数据） |
| 第 N 行无法解析 | 备份文件第 N 行数据损坏 |
| 能解析但无备份数据 | 这不是本应用的备份文件（缺少备份数据） |
| 图片 base64 解码失败 | 备份中有一张图片数据损坏，无法解码 |
| `QuotaExceededError` | 导入中途存储空间不足 |
| 其他 | 导入失败：<原始 message> |
| 有已写入内容被撤销 | 追加「，已自动撤销本次导入的内容」 |
| 回滚有清理失败 | 追加「（N 张图片未能清理，不影响现有数据）」 |

## 数据影响

- 无新增持久化字段、无 schema 变更、无备份格式变更。
- 新增只读行为：导入前读一次 `imageKeys()` 快照。
- 新增删除行为：仅在导入失败时删除**本次导入新写入**的图片（原图 + 对应缩略图键）。

## 验收标准

1. 导入前配额不足 → 在写入任何图片之前中止或经用户确认后继续，文案明确、非「格式不正确」。
2. 导入中途失败 → 本次新写入图片被全部回滚，IndexedDB 回到导入前状态；导入前已存在的同 ID 图片不被删除。
3. 损坏行 / 非备份文件 / 配额不足 → 各自给出对应文案。
4. 正常 v2 导入、v1 旧格式导入 → 行为与改造前一致（回归不降级，含缩略图补生成）。
5. 仓库中不再出现备份文件为未跟踪状态。
